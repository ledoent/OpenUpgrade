# Ledo 19.0 → 20.0 migration prep — roadmap

**Status**: 2026-05-16. Forward-looking; the 19.0 → 20.0 path is
blocked on Odoo SA shipping 20.0. This doc captures what we'll do
when 20.0 arrives, and what we can do in the meantime.

Companion to `docs/proof-18-to-19-migration.md` (what we have done)
and `docs/ledoent-roadmap.md` (current 19.0 work).

## Upstream signal — Odoo 20.0 timing

Per Odoo community sources, 20.0 is expected to ship at **Odoo
Experience 2026 (September 24-26, 2026)** in Brussels. General
availability typically 2–4 weeks after the conference. The official
roadmap was presented at Odoo Partner Days on **2 April 2026**;
no public 20.0 source code yet.

**Functional clusters expected** (community-sourced, not authoritative):

- Agentic AI baked into automation (vs rule-based)
- Major updates to Accounting, CRM, Inventory, HR, MRP, eCommerce
- POS, Sign, Phone, mobile / Payroll
- Website / Marketing tooling

For migration impact, the Accounting and Inventory clusters are the
biggest risk surface — those touch our most-tested workflows
(AP/AR/MRP/Stock).

## What we are blocked on

We cannot create a `20.0-mig-*` branch scaffold today because:

1. No 20.0 source code from `odoo/odoo` — the branch doesn't exist yet
   on the official repo
2. No `[20.0]` analysis files in `OCA/OpenUpgrade` —
   `openupgrade_scripts/scripts/<module>/20.0.x.y/upgrade_analysis.txt`
   is generated by the OCA analysis bot AFTER `OCA/OpenUpgrade` opens
   a `20.0` branch (typically 1-2 months after Odoo SA's release)
3. No OCA-side `20.0` branches on the OCA modules we depend on
   (account-financial-tools, mis-builder, rma, etc.)

**Expected timeline**:
- September 2026 — Odoo 20.0 ships
- October 2026 — `OCA/OpenUpgrade` 20.0 branch opens; analysis bot runs
- November-December 2026 — OCA module repos start opening 20.0 branches
- December 2026 – Q1 2027 — realistic window for our 19.0 → 20.0 work

## What we CAN do now (pre-20.0 release)

### 1. Promote the migrated 19.0 reference DB

The `agent_test_19_target` DB on the Hetzner runner is the output of
running `openupgrade:latest` against `seed_18_woodbimble_real` + the
AP + AR recipe deltas. It IS a 19.0 demo DB with realistic Ledo SMB
shape and our edge cases baked in. Promote it:

- `pg_dump -Fc agent_test_19_target` → `19.0-ledoent-real-oca.psql`
- Upload to fork release `databases`
- Use as the canonical "what Ledo prod will look like on 19.0"
  starting point for 19→20 testing

### 2. Pattern documentation captured

Already in place; reusable for the 19→20 cycle:

- `~/projects/ledoent/oca/openupgrade-lab/.claude/skills/openupgrade-contribute/SKILL.md` — contribution workflow
- `~/projects/ledoent/oca/openupgrade-lab/CLAUDE.local.md` — fork-only rule + anti-patterns
- `~/projects/ledoent/oca/openupgrade-lab/openupgrade/docs/ledoent-roadmap.md` — current 19.0 roadmap
- `~/projects/ledoent/oca/openupgrade-lab/openupgrade/docs/19.0-migration-runbook.md` — prod migration day checklist
- `~/projects/ledoent/odoo-agent-clerks/ROADMAP.md` — behavioral framework plan
- 3-tier fork CI workflow pattern (baseline / enriched / realistic+OCA)

### 3. Behavioral framework scaling (Phase 2-3 of odoo-agent-clerks)

This work is version-agnostic — pays off whether we're testing 19→20,
20→21, or any future migration. Doable now:

- **Phase 2** — add 1 more role (accounting), wire multi-role parallel
  run via Claude Code Agent tool. Catches lock contention + race
  conditions that single-role runs miss.
- **Phase 3** — scale to 9 roles total (purchasing, production planner,
  inventory planner, sales, shipping, receiving, accounting).
- **Phase 5** — UI navigation layer via chrome-devtools MCP. Adds the
  "every form opens and progresses" coverage that XML-RPC alone can't
  prove.

Estimated effort: 2–3 days for Phase 2-3, 1–2 days for Phase 5.

### 4. Lab infrastructure refresh (when 20.0 ships)

```yaml

  odoo-20:
    image: ${OPENUPGRADE_IMAGE_20:-registry.hz.ledoweb.com/openupgrade/openupgrade-20:latest}
```

Update `repos.yaml` to add `20.0` branch targets on each OCA repo
as they open them. Add `test-migration-19-to-20.yml` workflow.

### 5. Watch for upstream signals

Cron-able watches:
- `gh api repos/odoo/odoo/branches | grep 20.0` — when does Odoo SA
  create the 20.0 branch
- `gh api repos/OCA/OpenUpgrade/branches | grep 20.0` — when does
  OCA mirror it
- File-globber for new `*/20.0.*/upgrade_analysis.txt` in OCA's
  `openupgrade_scripts/scripts/` directory

A simple weekly `gh workflow` could open a tracking issue when any
of those signals appear.

## What we will NOT do prematurely

- **Create a `20.0-mig-*` scaffold branch on the fork** — there's no
  source code to base it on. Doing it before 20.0 ships creates dead
  scaffolding that drifts and confuses future work.
- **Author new edge-case data for 19→20** — no schema delta to test
  against. We don't know what'll change.
- **Open OCA PRs** — fork-only rule still in effect (set 2026-05-15
  in `CLAUDE.local.md`).
- **Force a 20.0 migration on Ledo prod before OCA's `[20.0][MIG]`
  upgrade scripts mature** — historically takes 3-6 months
  post-release before a critical mass of modules has migrations.

## Decision points / triggers

| Trigger | Action |
|---|---|
| Odoo SA creates 20.0 branch on `odoo/odoo` | Add `odoo-20` service to lab compose; create initial `20.0` branch on fork |
| First `[20.0]` analysis file appears in OCA/OpenUpgrade | Scaffold first `20.0-mig-*` test branch; verify CI fires |
| OCA hits ~50% of US-relevant module migration coverage | Start 19→20 fork-CI runs against our `19.0-ledoent-real-oca.psql` |
| Ledo / Kencove customer ready to migrate | Run behavioral framework's full 9-role loop pre→migrate→post |

## Open questions for review

1. Do we keep the 3-tier seed pattern (`baseline / enriched / realistic+OCA`)
   for the 19→20 cycle, or simplify to single `realistic+OCA` since the
   bloated seeds proved less useful?
2. Should the behavioral framework scale to 9 roles BEFORE 20.0 ships,
   or wait until we have a real 19→20 migration to validate?
3. Pinning policy: do we lock the migration image to a specific SHA
   before any production migration commitment, or keep `:latest`?
